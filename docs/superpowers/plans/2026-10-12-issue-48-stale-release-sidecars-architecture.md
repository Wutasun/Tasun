## 2. Verified defect

Two root-level files look like generic current release evidence but are not owned by the current publisher.

### 2.1 TASUN_REBUILD.txt

Current deployed-repository content:

```
version=20261012_tasun_v5_xidong_docs_r1150_84d0951c475b_release
releaseSequence=1150
```

The current formal release is R1152 / sequence 1152.

Repository history shows `TASUN_REBUILD.txt` was introduced by upload commit `abdbac17f2f6822c79fcd0cb2f3071e0231c8c30` and has not participated in subsequent exact releases.

### 2.2 SHA256SUMS.txt

The file still contains historical hashes from an R956-era package for:

- `TASUN_REBUILD`
- `TASUN_REBUILD_STAMP`
- `tasun-version.json`
- all four formal pages

Repository history shows it was introduced by upload commit `84122ab69eae4c81403e820cbf0867945b5cf29e` and is not regenerated by the exact publisher.

## 3. Consumer and deployment trace

Repository search finds no current source/workflow/runtime consumer for either:

- `TASUN_REBUILD.txt`
- `SHA256SUMS.txt`

The publisher defines:

- `VERSION_FILE = tasun-version.json`
- `REBUILD_FILE = TASUN_REBUILD`
- `REBUILD_STAMP_FILE = TASUN_REBUILD_STAMP`

and its GENERATED set contains only those three release files.

GitHub Pages artifact preparation uses root-level `rsync` and does not exclude generic `*.txt` files. Therefore both unmanaged sidecars are deployed even though final deployed verification does not validate them.

This creates a split between:

- machine-verified formal release authority: R1152;
- stale human-facing generic sidecars: R1150 / historical hashes.

## 4. Architecture options

### Option A — retire both unmanaged generic sidecars

Delete:

- `TASUN_REBUILD.txt`
- `SHA256SUMS.txt`

Add regression that requires both generic stale sidecars to remain absent.

Keep the existing publisher, canonical rebuild files, manifest SHA metadata, and deployed verifier unchanged.

#### Advantages

- removes the contradictory release surface completely;
- preserves one existing release authority;
- no duplicated digest generation;
- no new publisher responsibility;
- smallest implementation and maintenance surface;
- cleanup-only change should not require a new formal release sequence.

#### Costs / risks

- any undocumented external/manual process using one of these filenames would stop finding it;
- repository evidence currently finds no such consumer, so this is an external-process-only residual risk.

### Option B — adopt both sidecars into the exact publisher

Extend the current publisher to regenerate:

- `TASUN_REBUILD.txt` as a second textual release marker;
- `SHA256SUMS.txt` from the exact post-normalization page/version bytes.

Extend deployed verification to validate them.

#### Advantages

- preserves the filenames for unknown external/manual consumers;
- all deployed generic release artifacts would remain current.

#### Costs / risks

- creates duplicate representations of information already authoritative elsewhere;
- expands publisher GENERATED state and deployed verification scope;
- adds ordering requirements for digest generation because `tasun-version.json` contains per-page digests and the checksum file would digest the manifest/rebuild artifacts;
- increases future split-brain risk if any one representation is omitted from a release change;
- provides no proven runtime requirement.

## 5. Recommended architecture — Option A

**Recommend Option A.**

Reason:

The current system already has complete, verified release evidence:

- `tasun-version.json` — formal version / sequence / per-page metadata authority;
- `TASUN_REBUILD` — compact version + releaseSequence marker;
- `TASUN_REBUILD_STAMP` — exact build marker;
- page HTML embedded build stamps;
- manifest SHA fields;
- deployed exact four-page verification.

`TASUN_REBUILD.txt` and `SHA256SUMS.txt` add no proven behavior. Their generic names instead make stale data look authoritative.

The correct convergence is therefore to remove the unmanaged duplicate surfaces, not make the publisher maintain more copies.
