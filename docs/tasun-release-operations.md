# Tasun release repair and operation

The current baseline is main 326065efd4d (R1139). Preserve R1122's single lifecycle/render-commit authority and the later R1139 changes.

## One-time administrator prerequisite

In repository Settings > Pages > Build and deployment, set **Source = GitHub Actions** before releasing. This is an administrator operation, not a per-release operation. The former `PUT /repos/.../pages` failed with HTTP 403 in run 37770533571. Do not add a broad PAT or weaken repository permissions to make it work.

The workflow now reads the setting and stops with a setup instruction before generating or committing an artifact if it is not configured. `configure-pages` does not attempt automatic enablement.

## Verification

- `node --test tests/*.test.*`
- `node publish-version_tasun_project_autoscan.mjs --verify-only` is read-only and fails on sequence/hash/alias/rebuild mismatches.
- `TASUN_CHANGED_FILES=tasun-version.json node publish-version_tasun_project_autoscan.mjs` repairs metadata using the existing manifest build; do not use this to hide unversioned functional edits.
- A page/core change generates the next version via the existing publisher. All four document pages use one build; every alias, digest and sequence derives from it.
- Release uses a verified artifact only. If a concurrent push rejects the generated commit, stop and let the new source push create its own release; do not rebase and deploy stale generated bytes.
- Successful legacy `pages build and deployment` is not proof that the exact four-page workflow completed. Require the final `Verify deployed four-page build sequence and SHA` job.
